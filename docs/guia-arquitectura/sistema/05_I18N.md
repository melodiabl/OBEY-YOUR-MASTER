# Internacionalización integral

## Contrato

Usar un único resolvedor público que concilie `locales/` y el sistema legacy. Las claves son semánticas: módulo, entidad, acción/estado y campo. No usar el texto español como clave ni concatenar frases. Los errores de negocio se traducen al presentar, no dentro del repositorio.

Objetivo inicial: ES y EN revisados para todo el alcance publicado. PT-BR es ampliación propuesta. DE y el archivo legacy `in` requieren identificar idioma real y cobertura antes de activarlos. Conservar datos hasta conciliar; el nombre `in` no se convierte a otro locale por suposición.

| Superficie | Resolución objetivo |
| --- | --- |
| Panel público | Override autorizado del módulo → idioma guild → ES |
| Respuesta efímera | Preferencia usuario → locale interacción → idioma guild → ES |
| DM | Preferencia usuario → locale disponible → ES |
| Job | Resolver idioma al entregar salvo contrato que congele una plantilla/revisión |
| Tarjeta | Mismo locale, renderer y formatos que su mensaje asociado |
| Slash/opciones | Localizaciones admitidas por Discord; lógica e IDs independientes |

Fallback variante → idioma base → default. Mantener regiones cuando importen, sin cortar automáticamente todo a dos letras. Zona horaria IANA es otra preferencia: no se deduce del idioma.

## Organización propuesta

Catálogos por locale y módulo cuando se migre ese módulo. Un índice registra locales publicados, estado de revisión y mapping de aliases legacy. No mover todas las claves a la vez ni mantener dos archivos canónicos para el mismo texto.

Ejemplo de contrato, no archivo cargable:

| Clave | ES | EN | Variable |
| --- | --- | --- | --- |
| music.queue.added | Agregué «{title}» a la cola. | Added “{title}” to the queue. | title: texto escapado |
| tickets.close.confirm | ¿Cerrar el ticket {number}? | Close ticket {number}? | number: identificador visible |
| common.actions.retry | Volver a intentar | Try again | ninguna |
| config.conflict | La configuración cambió mientras la editabas. | The configuration changed while you were editing it. | ninguna |

Plurales requieren una implementación acordada. Propuesta: Intl.PluralRules y catálogos con variantes completas; si se adopta ICU, usar un solo parser y migrar contratos completos. No mezclar sintaxis ICU, `%s`, interpolación JS y llaves sin adaptadores delimitados.

## Variables y salida

Cada clave declara variables requeridas y sus tipos. Validar igualdad de variables entre idiomas y escapes. Nombres, URLs, títulos musicales y motivos de usuario se insertan como datos, no como plantilla ejecutable. Configurar allowed_mentions según intención; no permitir que una variable introduzca menciones masivas.

Guardar timestamps UTC y formatear con Intl/Discord timestamp cuando sirva. Tiempo relativo nativo de Discord no requiere editar el mensaje para cada actualización del cliente. No presentar ese mecanismo como una barra musical nativa.

## Cobertura obligatoria

Incluye comandos/opciones, ayuda, errores de validación, botones, menús, modales, placeholders, estados vacíos, confirmaciones, DM, jobs y texto dinámico de imágenes. Buscar hardcoded en todos los consumidores. Un conteo de claves igual no prueba que se consuman o que la traducción sea natural.

## Flujo para añadir idioma

Registrar locale y fallback → traducir catálogos del alcance → comprobar variables/plurales/longitudes → revisar por hablante → registrar localizaciones de comandos → comprobar recorridos en Discord → publicar. Si falta cobertura, mantener borrador y fallback; nunca mostrar nombres internos de claves al usuario.

No enviar motivos privados, tickets o gustos a un servicio externo de traducción automática sin una función y política explícitas. Los textos proporcionados por servidores se conservan en su idioma salvo edición voluntaria.
