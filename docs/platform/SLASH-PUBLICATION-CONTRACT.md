# Publicación slash · destino exacto y confirmación

`deployslash [GUILDID]` conserva nombres, alias, tipo, categoría y cooldown de 360 segundos. Sin argumento (o con `global`) prepara publicación global; un ID completo prepara solo ese servidor. Un ID inválido, extra o no accesible nunca pasa a global. Se retira el ID fijo anterior: solo el dueño actual del archivo persistente y con acceso fresco al origen puede preparar y confirmar, sin añadir Administrator. El destino de servidor se obtiene de nuevo y se coteja el miembro bot.

La preparación es de un solo uso, opaca, ligada a cliente/contexto/destino, con 30 segundos de vida. Muestra alcance, número de raíces e invocaciones, altas/cambios/bajas y advierte que se reemplaza el registro completo del alcance. Confirmar/Cancelar se ligan a actor, guild, mensaje y nonce. ACK, aviso previo y comprobación final de autoridad preceden a cualquier PUT; cancelación, vencimiento, fallo de mensaje o permiso no lo admiten.

Un servicio común coordina publicación manual y sincronización global del arranque, con una operación activa por cliente, rastreada por el cierre. Se rechazan catálogos vacíos, duplicados, no chat-input, inválidos o restringidos y respuestas ajenas a aplicación/alcance. El catálogo proviene solo de los schemas cargados, nunca de argumentos o JSON recibido por Discord. Antes de escribir se comprueba que el catálogo y registro remoto siguen siendo los de la vista previa. Una respuesta GET fallida no significa registro vacío.

Se compara semántica, no IDs/versiones ni orden de raíces. Se normalizan defaults, localizaciones vacías/nulas y espacios exteriores de descripciones que Discord recorta; se conserva orden de opciones/choices. contexts/integration_types no definidos por el catálogo se dejan como están para comandos existentes y usan los defaults de Discord para comandos nuevos. Un registro igual no se sobrescribe. Un tipo remoto no soportado detiene la operación, sin borrar otros tipos. La misma política de publicación global automática del arranque permanece, pero usa el servicio compartido y omite PUT cuando no hay diferencias; no hay reintento automático de una escritura incierta. El transporte de escritura es separado, con retries=0, rechazo de rate limits y timeout de diez segundos, sin modificar el REST compartido.

Una respuesta PUT solo confirma éxito si la lista devuelta pertenece a aplicación/destino y coincide con lo enviado, incluidos nombre, tipo, descripción, opciones y permisos controlados. No acredita propagación a todos los clientes Discord. Rechazo o plazo de 20 segundos agotado después de admitir PUT se comunica como no confirmado; antes de admitir, una lectura tardía no produce efecto. La reserva se conserva hasta que termine la promesa subyacente, aunque el llamante haya agotado su espera. La comprobación remota no es un CAS de Discord: otro proceso puede cambiar el registro después del último GET. No hay recibo duradero ni coordinación entre procesos; siguen pendientes.

Errores y fallos de idioma/entrega se contienen en es/en, sin stack, secretos, código dinámico, DM ni canal alternativo. Los códigos de idioma heredados válidos de/in conservan fallback español. La instrumentación y cooldown del dispatcher mantienen su comportamiento.

Pruebas con SDK real y REST/miembros/mensajes ficticios; no se publican comandos ni se invocan mensajes reales. El despliegue exige un dry-run de solo lectura que confirme que el registro global real ya coincide, para que el arranque de esta entrega no pruebe un PUT real. Conservar las tres fuentes/25 pruebas originales y retirar verificadores temporales tras guardar TAP/JSON. G01/G02 y recorrido real quedan abiertos.

Fuente: [Application Commands de Discord](https://docs.discord.com/developers/interactions/application-commands#bulk-overwrite-global-application-commands): las operaciones bulk reemplazan el registro de su alcance; no se usan como fallback de un destino de servidor desconocido.
