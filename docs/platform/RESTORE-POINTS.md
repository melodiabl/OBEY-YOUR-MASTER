# Puntos de restauración de estructura

T27 parcial. Web y `/config architect accion:copia` solicitan `architect.backup` en el servicio de jobs compartido. Permisos `ManageGuild` frescos, actor/guild derivados de la sesión/interacción, CSRF HTTP, respuestas privadas/no-store y scope por creador. GET lista hasta 20 copias; GET por ID inspecciona la estructura real guardada. Un ID de otra persona devuelve 404.

Cada punto es inmutable y versionado: UUID, creador, fecha, origen, job, snapshot, revisión de estructura y SHA-256 del snapshot íntegro. El índice `(guildId, jobId)` evita duplicados al recuperar un worker que murió después de persistir. Se rechaza corrupción al inspeccionar y no se almacena configuración, tokens, sesiones, mensajes, miembros, hilos ni datos externos. Colección nueva `ArchitectRestorePoint`; el modelo/cron/comandos legacy de `discord-backup` no se migran ni sobrescriben.

Completitud declarada `structure_only`: canales/categorías, roles y overwrites. No se promete backup completo de OBEY ni restaurar IDs/enlaces/mensajes eliminados. Aún pendientes configuración portable/referencias de módulos, import/export validado, retención/scheduler, comparación y restauración confirmada con remapeo. No hay restauración automática ni botón sin backend.

Los handlers Architect se ejecutan bajo lease por guild: `SET NX PX`, token UUID, renovación cada 10 segundos con TTL de 30, compare-and-renew y compare-and-delete Lua. El productor falla pronto ante Redis caído. Un worker que pierde su token deja de publicar checkpoints/copias; contención mueve el job a delayed sin agotar los tres reintentos de fallo. Dos guilds distintas pueden trabajar en paralelo. El handler de backup comprueba además token/cancelación Mongo antes de persistir. Cancelación cooperativa puede conservar una copia ya guardada; no se elimina como efecto secundario.

El lease sigue el patrón oficial de [Redis](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/), y la espera sigue [DelayedError de BullMQ](https://docs.bullmq.io/patterns/process-step-jobs). Es una instancia Redis, sin garantía de exclusión ante failover o solicitudes Discord en vuelo tras pérdida de lease. Las ediciones compatibles añaden guard/journal duraderos y detención ante respuesta incierta (`APPLICATIONS.md`). El lease solo no hace idempotente una creación REST; esas creaciones siguen pendientes.

Verificación: `test/restore-points.test.js`, `test/guild-lock.test.js`, rutas/command/jobs; `scripts/verify-jobs-runtime.js` usa MongoDB/Redis/BullMQ reales aislados y prueba contención, paralelo, renovación, token reemplazado, scopes y recuperación post-persistencia. Chromium verifica crear/inspeccionar, límites visibles, dos pestañas, reload, revocación/respuesta tardía y móvil sin overflow/errores. Evidencia en `evidence/jobs-*.json/png`.
