# Aplicación confirmada de estructura

T28 parcial: backend y web implementan nombres de canales/categorías/roles existentes, temas de canales de texto, colores de roles y creaciones básicas con IDs lógicos→reales persistidos. Admiten roles nuevos sin permisos en posición inferior y categorías/texto/voz sin sobrescrituras, usando la posición predeterminada de Discord. Los permisos de roles y las sobrescrituras de canales de texto/voz existentes ya se aplican. Cambios de categoría de texto/voz existentes se aplican conservando sus permisos. Reordenamiento de recursos existentes por lote añadido. Ordenar creaciones o combinar orden/parent en el mismo tipo, permisos de categorías, eliminaciones y módulos siguen bloqueados para ejecutar. El editor permite diseñar otros cambios y guardarlos.

Las dependencias se ordenan roles (incluido lote de orden) → categorías → canales → movimientos entre categorías → lote de orden de canales → permisos de roles → sobrescrituras de canales. Cada categoría obtiene un ID real antes de crear sus hijos. La preparación muestra el límite del orden predeterminado; las posiciones 1 de roles nuevos y 0 de canales nuevos son los valores admitidos para esta creación básica. No se manda `position` al SDK: `RoleManager.create` añadiría otra mutación. Se permite renumeración del proveedor solo conservando el orden de todos los recursos existentes y todos sus demás campos capturados. Un rol nuevo debe quedar debajo de los existentes, excepto `@everyone`. No se promete un orden personalizado de nuevos roles entre sí.

Preflight exige permisos efectivos de administrador/bot y acceso al padre, `ViewChannel` para ambos en los recursos nuevos y `ViewAuditLog` del bot. Comprueba 250 roles, 500 canales, 50 hijos por categoría y bitrate según `guild.maximumBitrate`. Categorías con sobrescrituras bloquean estas creaciones básicas: no se convierten silenciosamente en canales públicos ni se inventa una herencia de permisos que el blueprint no contiene. No son todavía todas las restricciones/capacidades del guild.

La aplicación está cerrada por defecto. Un operador debe configurar IDs numéricos concretos en `OBEY_ARCHITECT_APPLY_GUILDS` para un canary previamente autorizado. Configurar Redis no habilita este flag. No se configuraron guilds, reinició el bot, publicó comandos ni ejecutó REST Discord real. Los scripts usan proveedores mutables de fixture en redes aisladas.

La edición de color solo admite roles con estilo simple conocido. Gradientes/holográficos se bloquean, y estado desconocido no se considera seguro. El snapshot guarda los tres colores conocidos en metadata `roleColors` y los incorpora a la revisión; una modificación de color secundario invalida el plan aunque el primario no cambie. Snapshots anteriores sin esa metadata siguen legibles. Se utiliza `colors` del SDK, evitando la opción antigua `color` que limpia los colores secundarios. Ver [contrato de colores de discord.js 14.27.0](https://discord.js.org/docs/packages/discord.js/14.27.0/RoleColorsResolvable%3AInterface).

## Permisos y acceso resultante

`handlers/architect/permissions.js` calcula el acceso con roles actuales de miembros forzadamente recargados y el snapshot observado. Sigue precedencia everyone → OR de roles → sobrescritura everyone → deny/allow agregados de roles → miembro, con bypass del propietario/Administrator y restricción de timeout en canales. Si faltan memberships/roles/snapshot, el preflight queda incompleto. Contraste determinista con `GuildChannel.permissionsFor` del SDK instalado; no se acepta una caché ausente como acceso concedido.

El plan simula cada cambio en orden, incluidos estados intermedios. Preserva capacidades administrativas originales y acceso ViewChannel/ManageChannels/ManageRoles de canales que ya tenían esas capacidades; el actor debe mantener ManageGuild. Cada canal con sobrescrituras modificadas exige los tres permisos después del cambio. Una secuencia que pierde acceso primero y lo recupera al final se bloquea. Los grants deben pertenecer tanto al actor como a OBEY; también se comprueba la retirada de denies, que puede devolver acceso heredado. La política requiere ManageRoles global y permisos concedidos/denegados globales para ambos: no aprovecha excepciones locales del proveedor.

Solo cambia permisos de roles existentes editables y sobrescrituras completas de texto/voz existentes. Se mantienen IDs/orden/campos ajenos y destinos member ya existentes; no se crean overwrites para miembros nuevos. Los destinos de roles lógicos se remapean desde el journal. Permisos de categorías siguen bloqueados porque Discord puede propagar cambios a hijos sincronizados; esa cascada necesita diff/preflight explícitos antes de admitirse. Nuevos roles/canales siguen creándose sin permisos personalizados.

Antes y después de cada PATCH se verifican estructura/permisos/revisión y se completa el checkpoint CAS. Una respuesta incierta de permiso conserva `executing`/guard para revisión y no se reproduce. Las asignaciones de roles a miembros pueden cambiar fuera del job: se recargan para cada preflight; no hay CAS ni promesa de atomicidad con Discord. Restricciones completas de capacidades/MFA/integraciones y recuperación manual siguen pendientes.

El inspector ofrece flags básicos del rol y permitir/denegar/heredar por rol en texto/voz. Campos desconocidos y otros destinos se conservan; no hay creación de member overwrites. Revisión muestra destinatarios y nombres de permisos; confirmación advierte su impacto. Managed/everyone/protegidos y controles de nuevos recursos/categorías se mantienen bloqueados. El contador distingue pasos de permisos de recursos editados.

Fuentes: [permisos Discord](https://docs.discord.com/developers/topics/permissions), [modificar canales](https://docs.discord.com/developers/resources/channel#modify-channel), SDK instalado. T26/T28/T30 siguen parciales.

## Cambios de categoría

T26/T28/T30 parcial: se aplica `parentId` de texto/voz existentes, incluido mover al nivel raíz (`null`) y a una categoría creada antes en el mismo job, remapeando su ID lógico. `diff.resourceType` permite rechazar categorías/avanzados y `before.position === after.position` impide mezclar reordenamiento. El SDK recibe `parent` y `lockPermissions: false`, sin `position` ni `permissionOverwrites`; se verificó con GuildChannelManager instalado y REST sustituido. Una llamada de edit no debe disparar su segundo request de `setPosition`.

Preflight usa snapshot fresco y miembros recargados. Requiere ViewChannel/ManageChannels actuales en canal y destino para actor/bot, además de Connect en voz. Las restricciones de timeout bloquean actores no exentos; propietario/Administrator mantienen la excepción del proveedor. Un destino pendiente de creación usa sus permisos globales solo cuando la categoría aún tiene ID lógico; un ID real con caché ausente queda desconocido. La categoría debe conservar las mismas sobrescrituras guardadas que el canal antes de mover, evitando discrepancias de privacidad silenciosas. Se permite salir a raíz manteniendo las sobrescrituras. El plan se rechaza antes de efectos si supera las 1000 operaciones que soporta el journal. No se admiten sincronización solicitada ni movimientos que requieren antes otra política de permisos.

La simulación ordenada comprueba el máximo de 50 hijos por categoría después de cada creación y movimiento. Un estado final que cabe no autoriza una fase intermedia llena; no reordena automáticamente vaciados/ciclos. Los permisos posteriores pueden cambiarse explícitamente en su fase; al recuperar/validar un movimiento ya checkpointed no vuelve a exigir la igualdad antigua de overwrites, pero sí acceso/capacidad actuales. No se reejecuta REST de pasos completados.

La revisión muestra categorías anteriores/nuevas y explica la conservación de permisos. Copia previa, snapshot/contador CAS, aislamiento por guild y guard funcionan como en permisos. Compara toda la revisión esperada después del PATCH y del preflight: renumeración no prevista u otro cambio detiene el job para revisión. Un paso executing incierto no se reconcilia por nombre/parent ni se reproduce automáticamente. No hay rollback automático.

El compromiso de conservar permisos corresponde a este movimiento. No significa que futuros cambios de categoría de otros actores no puedan propagarse: `GuildChannel.permissionsLocked` en el SDK se deriva de comparar overwrites del canal y su padre. La cascada/sync de cambios futuros debe tratarse antes de habilitar permisos de categorías. El planner completo de orden combinado con creaciones/cambios de parent sigue pendiente.

## Orden de recursos existentes

Se aplica un PATCH por tipo con la lista `{id, position}` de recursos existentes cambiados, a través del REST manager compartido del SDK y su audit reason. Los managers `setPositions` instalados no transmiten reason; el helper usa sus mismas rutas nativas para conservar la protección de replay y los buckets. No envía permisos, padres, nombres ni colores. El snapshot esperado se ordena nuevamente por posición/ID antes de comparar toda su revisión con una lectura fresca.

Preflight conserva el conjunto de posiciones por tipo/categoría y bloquea cruces de recursos protegidos. `@everyone`, managed, avanzados y IDs protegidos se conservan; roles cambiados deben estar bajo actor/bot en posiciones actuales y deseadas, con excepción de propietario solo para el actor. Canales requieren ViewChannel/ManageChannels efectivos, Connect en voz y no estar sujetos a un timeout que los impida. La UI Subir/Bajar solo intercambia canales del mismo tipo/padre y mantiene undo/redo.

No mezcla creación y orden del mismo tipo ni cambios de parent con orden de canales en una aplicación. Esta restricción evita adoptar renumeraciones y pasos intermedios no descritos. Aplicar la creación/categoría primero y abrir una propuesta fresca permite ordenar después. Un lote representa un paso real, aunque afecte varios recursos; el resultado cuenta recursos editados únicos y recursos ordenados. Una respuesta incierta conserva executing/guard y no reproduce el PATCH; no hay rollback automático.

Un cambio externo o normalización distinta del proveedor después del lote detiene el job. No se promete una transacción con Discord, ni aceptación de canary real. Tests y fixtures prueban conjuntos/anchors/jerarquía/tipos/permisos, DTO/checkpoints/copias y ausencia de replay. Chromium usa los controles reales para ordenar roles/texto, verifica protección y posiciones de voz, confirmación y copia anterior.

## Preparación y confirmación

`POST /api/architect/:guildId/applications` valida un blueprint contra un snapshot fresco, calcula diff y preflight, agrupa ediciones por recurso y crea un plan privado. El actor/guild provienen del contexto autenticado, con permisos OAuth frescos y CSRF. Un plan vacío o con efectos no soportados se rechaza. El preflight para ejecutar comprueba además `ManageGuild` del actor y `ManageChannels` efectivo en cada canal, sin tratar un permiso global como garantía de acceso local.

Plan y payload tienen versión 1. El plan contiene snapshot/blueprint/operaciones/revisión y caduca a los 15 minutos, con TTL Mongo. Se devuelve un token de confirmación aleatorio de 256 bits; solo su hash SHA-256 se persiste en el plan. La web muestra antes/después y requiere confirmación explícita. Cambiar la propuesta elimina su confirmación local.

`POST /api/architect/:guildId/applications/confirm` acepta únicamente `{id, confirmation, revision}`. Comprueba scope, hash en tiempo constante, revisión, caducidad y drift antes de marcar confirmado. El servicio de jobs solo acepta `architect.apply` con un `applicationId` cuyo payload confirmado proviene del servidor; el cliente no proporciona payload de ejecución. La clave `apply-<plan UUID>` hace idempotentes confirmaciones concurrentes o con respuesta perdida. La marca confirmada y la solicitud son dos writes: repetir la confirmación repara el caso donde el segundo write falló; no se promete transacción entre documentos.

## Ejecución y recuperación

Mongo conserva payload inmutable, revisión esperada, referencia de copia, pasos y contador real. Las aplicaciones con creaciones, movimientos, orden o permisos incluyen `executionSnapshot` y `executionIdMap`: snapshot observado, revisión, mapa y contador se actualizan en el mismo CAS que completa el paso. La lista de jobs excluye esos campos internos; el resultado privado completado incluye mapa y conteos reales, separados en `creates`, `edits` (recursos distintos), `moves` (cambios de categoría), `reorders` (recursos ordenados) y `permissionChanges` (pasos de permisos). BullMQ entrega solo el ID del registro. El worker comprueba de nuevo permisos del actor, canary y token Mongo antes de entrar al lease Redis por guild. El ejecutor valida versión/scope, blueprint, diff y operaciones del payload.

Antes de efectos reclama además `ArchitectGuildOperation` por guild. Este guard duradero no caduca: un lease Redis perdido no permite a otra aplicación atravesar una edición incierta. Captura una copia `before_apply` y exige que su revisión coincida con la esperada. Antes de cada edición lee estructura, revisa permisos/hierarchy efectivos y vuelve a comprobar la revisión después del preflight.

Cada paso se escribe `executing` **antes** de REST, mediante CAS del token y estado/cancelación. Después de editar compara el snapshot completo con la revisión esperada para ese cambio. Tras crear verifica el ID devuelto, campos de la propuesta, dependencias remapeadas, un único recurso añadido y conservación del resto; repite permisos y lectura antes del checkpoint. Una modificación externa o normalización no prevista detiene la ejecución. Solo entonces persiste `completed`, revisión y contador juntos. Un checkpoint completado no se vuelve a ejecutar. Un crash después del último checkpoint puede recuperar resultado y liberar el guard sin repetir efectos.

El transporte mantiene el REST manager y los buckets compartidos. Un wrapper de `makeRequest` aplica únicamente a POST de roles/canales y PATCH de roles/canales con motivo `OBEY Architect`: transforma errores de red y 5xx en error no reintentable por el SDK. Los GET y creaciones legacy conservan su comportamiento; un 429 definitivo sigue el bucket de discord.js. No se cambia globalmente `retries` ni se crea otro cliente con token. Se verificó contra la implementación instalada de `@discordjs/rest`.

Si REST, lectura posterior, lease o checkpoint falla tras `executing`, una creación intenta reconciliar **sin repetir POST**. Consulta hasta 100 entradas recientes del tipo de creación y exige exactamente una del bot con el motivo de ese job/paso. Su target debe ser nuevo respecto al último snapshot persistido y la estructura completa debe coincidir con esa única creación. Vuelve a comprobar permisos, lease/token y revisión antes de guardar ID y checkpoint. También usa esta comprobación al recuperar un paso `executing`. Un nombre igual o ausencia de auditoría nunca autorizan recrear. Si las pruebas no bastan, el job termina `application_needs_review` y conserva el guard; un job terminal no se reintenta automáticamente cuando aparezca más tarde la auditoría. La herramienta de revisión/reanudación manual aún está pendiente. Una edición existente incierta sigue requiriendo revisión.

Una segunda aplicación falla mientras existe ese guard. Cancelar durante una solicitud REST en vuelo puede dejar el efecto aplicado; mantiene el guard y los pasos inciertos. La UI explica que cancelar no revierte lo ya realizado. Una confirmación caducada puede cerrar el checkpoint de una última creación ya comprobada, pero no iniciar nuevos efectos.

El guard solo se libera al completar todos los pasos o tras un aborto duradero, por CAS, antes de cualquier edición. Ese aborto marca `executionAborted` y prohíbe `startEdit`, impidiendo que un worker antiguo libere protección sobre un nuevo worker. No hay botón de desbloqueo ni borrado automático por timeout. Reconciliar una ejecución incierta requiere comprobar la estructura real, el journal y la copia; herramienta de recuperación/rollback y aceptación real quedan pendientes. No borrar un guard a ciegas.

Discord no ofrece una transacción/CAS para esta secuencia. Cambios humanos, comandos legacy y otros bots no adquieren nuestro lease. Se detecta drift antes/después de cada edición, pero no se promete atomicidad ni exactamente una llamada REST. El cliente discord.js administra sus buckets de rate limit; no se añadieron sleeps ni reintentos de mutación paralelos.
