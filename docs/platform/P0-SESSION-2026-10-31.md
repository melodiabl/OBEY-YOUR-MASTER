# P0-C3 · sesiones y rutas base · 31/10/2026

Se revisaron las trece rutas de base de `platform`: health, landing, login, callback OAuth, logout, panel, actualización de servidores, estadísticas JSON/SSE, dashboard, contexto de Next y las dos entradas `/app`. Se conserva OAuth identify/guilds, la cookie firmada y el almacén `dashboard_sessions`; no se amplían permisos de servidor. La evidencia distingue fixtures, navegador, Mongo aislado, imagen y despliegue. [Resultados](evidence/p0-session-20261031.json).

## Autoridad y respuestas

El backend recarga la sesión vigente, mantiene actor y generación de login, comprueba caducidad y coordina una renovación por sesión. El proveedor devuelve datos sin mutar una referencia antigua de sesión. Un resultado tardío no sobrescribe tokens renovados ni reconstruye una sesión cerrada. Los fallos transitorios devuelven indisponibilidad y conservan el login; la revocación confirmada del token se distingue de una caída de red.

Las consultas de permisos comprueban otra vez la sesión después de esperar a Discord, validan el formato de la lista y esperan el guardado antes de continuar. Dashboard y contexto de Next usan la misma comprobación y no reutilizan permisos antiguos si el proveedor falla. Perfil y guilds salen por listas explícitas de campos; nunca se renderizan tokens OAuth. El recuento de comandos del panel procede de las entradas cargadas, sin la constante 625.

Las respuestas privadas llevan `private, no-store` y `Vary: Cookie`. Health expone únicamente estado, disponibilidad de base/música y uptime. Las estadísticas anónimas contienen solo guilds, usuarios, reproductores activos y fecha de actualización; las métricas internas mantienen acceso autenticado. SSE exige sesión y la verifica antes de cada entrega, termina al revocar/caducar y limita el búfer de clientes lentos. No expone IDs, nombres o estados musicales privados por la estadística pública.

## Login, logout y ordenación

State tiene formato acotado y se consume antes del intercambio, una vez por sesión en este proceso. El callback guarda un pendiente opaco, valida que siga vigente y regenera el SID con `Session.regenerate`. Las peticiones de token/perfil/guilds tienen timeout y no siguen redirecciones del proveedor. La URL de retorno sigue limitada a `/app` o `/dashboard`.

El adaptador conserva la interfaz pública de Store (`get/set/destroy/touch`) y la API pública de Session; no llama a `store.generate`. Creación inicial y cambios de credenciales/state requieren capacidades del servidor ligadas a SID, objeto y estado esperado. Los estados anónimos también están protegidos: una respuesta antigua no puede restaurar una state consumida ni un pendiente después de logout. Las capacidades de peticiones distintas no se pisan. Las sesiones previas sin CSRF adoptan el valor del ganador de una inicialización concurrente sin destruir su login.

Logout confirma la eliminación local antes de anunciarla, desconecta los sockets de ese SID y solicita, cuando está disponible, la revocación del token de la sesión actual con timeout acotado. Para impedir que una respuesta OAuth tardía vuelva a entregar acceso, el SID previo conserva solo una fila de enlace al sucesor y su cookie/TTL: **sin perfil, tokens, state o pendiente reutilizable**. Logout con una cookie anterior elimina también la sesión sucesora y sus enlaces. Las lecturas se ordenan con la rotación para no observar un hueco intermedio. La eliminación de cadenas tiene un límite de 256 nodos; excederlo falla sin anunciar logout confirmado.

La fila mínima de enlace vive en la colección y política TTL existentes. No amplía la retención de tokens previos ni obliga a borrar perfiles/configuración del bot. La ordenación de operaciones es para el proceso único actual: la atomicidad entre procesos y aceptación de takeover siguen en P5. La recreación en Mongo aislado demuestra el formato persistido y la revocación de la sesión hija; no acredita por sí sola una arquitectura distribuida.

## CSRF y transporte

Se conserva HttpOnly/SameSite=Lax y Secure cuando la URL pública es HTTPS. La emisión ocurre tras guardar la nueva sesión; no se hereda el CSRF del login anterior. Las mutaciones con usuario requieren su token y el Origin configurado cuando se envía; también se rechaza un Origin ajeno en logout anónimo. Los valores CSRF no se generan y pierden durante una recarga intermedia.

La base añade `nosniff`, denegación de frames y política de referencia del mismo origen; no impone una CSP de scripts que rompa las pantallas existentes. Los errores de sesión anteriores a la respuesta devuelven 503. Si las cabeceras ya salieron (por ejemplo al cerrar SSE), se usa la vía de error de Express y no se intenta una segunda respuesta. La prueba de navegador detectó ese fallo durante la implementación; se corrigió antes de desplegar.

## Comprobaciones y límites

Casos de lectura obsoleta, logout durante renovación/intercambio/rotación, cookie OAuth tardía, doble callback, CSRF concurrente, cambio de actor, fallo de proveedor/almacén, revocación de permisos y stream cerrado. Express real comprueba las trece rutas; Mongo temporal comprueba el adaptador real `connect-mongo`. No se usan cookies, cuentas o bases de datos de usuarios reales para estas pruebas.

El conector Chrome MCP no arrancó bajo root. El recorrido se verificó con Chromium headless/CDP, usuario `nobody` y perfil/contextos temporales: aislamiento entre contextos, lista autorizada, retirada del servidor revocado, actualización con CSRF, cookie HttpOnly/Lax, formulario de logout y stream/tab anterior denegados; sin excepciones JS. No se usó un perfil personal. El servicio fixture no se incluye en la imagen ni en producción.

La revisión independiente encontró carreras en state anónima, errores de recarga, rotación y CSRF legado; se corrigieron y se añadieron casos específicos. El último borde de cookie tardía y el uso exclusivo de la API pública se verifican con regresiones reales de Express/Mongo. La revisión no se presenta como aceptación completa del resto de rutas o negocio.

Inventario: 661 comandos, 776 alias y 95 rutas; la revisión trazada pasa a **52 grupos/168 comandos/34 rutas**, con 493 comandos/61 rutas pendientes en sus capacidades. Estas trece rutas se registran en una intención de plataforma; no se aceptan por arrastre música, Architect, configuración ni soporte. G01/G02/G25 y la rotación Mongo del proveedor siguen abiertos. No se efectuó un login OAuth de una persona real ni la aceptación funcional en dos guilds: esa aceptación de negocio conserva P2.
